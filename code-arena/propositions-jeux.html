🦎 Le Festin du Caméléon

Le caméléon doit manger le plus de fruits possible sur une grille — un défi de code d'optimisation. Voici les 3 designs retenus, entièrement spécifiés pour servir de référence à l'implémentation.

⚙️ Contrainte d'architecture à connaître avant de coder

Le moteur actuel (GameRunner.php) est « one-shot » : le code joueur s'exécute une seule fois (toute sa sortie d'un coup), puis le référé simule et renvoie verdict + score + replay. Il n'y a pas encore de boucle tour par tour interactive.

✅ Compatible directement : tout jeu où la grille est connue d'avance et le joueur émet sa séquence complète d'actions → Design 1 (Langue) et Design 2 (Couleurs).

⚠️ Nécessite une adaptation : tout jeu « réactif » (le joueur découvre la carte au fil du jeu) → Design 3 (Brouillard). Faisable seulement en version « parcours aveugle », ou en construisant une infra interactive (gros chantier).

Design 1 — La Langue Extensible

chameleon-tongue
Mise en place★★☆☆ one-shot ✓ compatible

Marche pour te déplacer, ou tire ta langue pour gober un fruit à distance — chaque action compte, dose-les bien.

Objectif

Le caméléon dispose d'un budget d'actions. Une action = soit avancer d'une case, soit tirer sa langue dans une direction pour manger le premier fruit aligné à portée. L'enjeu : maximiser les fruits mangés. Tirer la langue permet d'économiser des déplacements → c'est le cœur de l'optimisation.

Contrat d'entrée / sortie

Entrée (stdin) — connue d'avance
# cols rows portee budget
8 6 3 12
# grille : . sol  # mur  S départ  F fruit
S....F..
..#..#..
..F...F.
....#...
F..#..F.
......F.
Sortie (stdout) — 1 action / ligne
MOVE R   # avance d'une case
MOVE R
TONGUE R # gobe le 1er fruit à droite
MOVE D
TONGUE D
# ... ≤ budget actions

Mécanique de simulation (logique du référé)

  • MOVE U|D|L|R : déplace d'une case. Viser un mur ou sortir de la grille = action perdue (le caméléon ne bouge pas), pas de crash.
  • TONGUE U|D|L|R : projette la langue jusqu'à portee cases. Elle s'arrête sur le premier fruit rencontré (mangé) ou sur le premier mur (rien mangé).
  • Chaque action consomme 1 du budget. Les actions au-delà du budget sont ignorées.
  • Chaque fruit ne peut être mangé qu'une fois.

Score & victoire

Score proportionnel aux fruits mangés : score = round(maxScore × fruits_mangés / total_fruits). Verdict passed si tous les fruits sont mangés, sinon failed mais le score partiel récompense l'effort.

  • Émet une frame par action (avec tongueTip pour animer la langue).

Design 2 — Caméléon Caméléon (couleurs)

chameleon-colors
Mise en place★★☆☆ one-shot ✓ compatible

Un caméléon ne mange un fruit que s'il a pris sa couleur — planifie tes changements de peau pour perdre le moins d'actions possible.

Objectif

Chaque fruit a une couleur. Pour manger un fruit, le caméléon doit d'abord changer la couleur de sa peau pour qu'elle corresponde. L'enjeu : ordonner ses visites pour minimiser à la fois les déplacements ET les changements de couleur (un TSP enrichi d'un coût de transition).

Contrat d'entrée / sortie

Entrée (stdin) — connue d'avance
# cols rows budget
8 5 16
# . sol  # mur  S départ
# R/G/B = fruit rouge/vert/bleu
S...R..G
..#...#.
.B...R..
..#.G.#.
.....B.R
Sortie (stdout) — 1 action / ligne
MOVE R
SKIN R   # devient rouge
MOVE R   # arrive sur un fruit R → mangé
SKIN G
MOVE D
# ...

Mécanique de simulation (logique du référé)

  • MOVE U|D|L|R : déplace d'une case (mur/bord = action perdue).
  • SKIN R|G|B : change la couleur de peau courante (coûte 1 action).
  • Quand le caméléon est sur une case fruit et que sa peau == couleur du fruit → le fruit est mangé automatiquement. Mauvaise couleur = rien ne se passe (le fruit reste).
  • Chaque action consomme 1 du budget.

Score & victoire

Identique au Design 1 : score = round(maxScore × fruits_mangés / total), passed si tout est mangé. Le budget serré force à minimiser les SKIN superflus.

Notes référé (referee.py)

  • Parse la grille + couleur de chaque fruit. État = (position, peau).
  • Rejoue les actions ; après chaque MOVE, teste si peau == couleur du fruit sous le caméléon → mange.
  • Émet une frame par action avec la peau courante (pour le teintage du sprite).

Notes viewer (PixiJS)

  • Base = viewer du Labyrinthe. ~85 % réutilisable (le plus simple des trois côté rendu).
  • Ajout : fruits colorés + teintage du sprite caméléon (PixiJS sprite.tint) qui change à chaque SKIN — visuellement « waouh » et trivial techniquement.

Design 3 — Vision Limitée (brouillard)

chameleon-fog
Mise en place★★★★ ⚠ adaptation requise

Le caméléon ne voit que les fruits proches : il doit explorer pour les découvrir tout en les collectant.

Objectif

Le caméléon ne « voit » que les fruits dans un rayon de vision. Il doit explorer la carte pour révéler les fruits cachés puis les manger, dans une limite de tours. C'est un mélange exploration + collecte.

⚠️ Le point bloquant

Cette idée, dans sa version réactive (le joueur reçoit à chaque tour les fruits visibles et décide en conséquence), suppose un dialogue tour par tour entre le code joueur et le référé. Or le GameRunner actuel ne fait qu'un seul échange (le joueur écrit tout, puis le référé lit tout). Deux voies possibles :

VoieDescriptionCoût
A — Parcours aveugle
faisable maintenant		 Le joueur connaît les murs mais PAS les fruits. Il émet un parcours fixe ; le référé mange tout fruit qui entre dans son rayon de vision pendant le trajet. Score = fruits trouvés. → devient un défi de couverture de terrain (one-shot, compatible). ★★ comme les autres
B — Vrai tour par tour
gros chantier		 Construire une infra interactive : exécuter le code joueur en mode boucle, lui réinjecter l'état à chaque tour. Modifie GameRunner, PistonService et le protocole. Réutilisable ensuite pour Botnet / Don't Panic. ★★★★+ + risque

Contrat (voie A — parcours aveugle, one-shot)

Entrée (stdin)

10 8 2 40
# murs connus, fruits CACHÉS
S.........
..####....
..........
....##....
..........
Sortie (stdout)

MOVE R
MOVE D
# un parcours couvrant la carte
# le référé mange les fruits
# vus dans le rayon `vision`

série 5 → 🔴🔴🔴🔴🔴 (5 rouges)

série 1 → 🔵 (1 bleu) OK

Le code doit résoudre un puzzle d'affectation couleur↔taille avant de bouger. Se tromper de répartition = blocage.

Le code doit faire un BFS qui interdit les cases de sa couleur. C'est le « aha ! » du jeu.

⏱️ 3. Le budget serré

Le nombre max d'actions (MOVE + SKIN). Au-delà, tout est ignoré. (Solution optimale ≈ 32 actions.)
NIVEAU 1 · budget = 60
trajet gaspilleur : 55 actions

Énorme marge : même un trajet brouillon, avec des allers-retours et trop de SKIN, passe.

Pas besoin d'optimiser. On ramasse dans le désordre.

NIVEAU 5 · budget = 35
trajet gaspilleur : 55 actions → ❌ tronqué
trajet optimisé : 32 actions → ✅

La barre blanche = le budget. Le gaspilleur déborde et ne finit pas ses séries.

Le code doit minimiser trajet + changements de peau : un mini problème du voyageur de commerce (TSP).

🎯 Mon conseil

  • Design 2 — Caméléon Caméléon (couleurs) : le meilleur rapport effet/effort. Rendu très lisible (le caméléon change de teinte, c'est sa signature), logique propre, zéro changement d'infra. Idéal pour un premier ajout.
  • Design 1 — La Langue : tout aussi compatible, un cran plus de travail sur l'animation, mais gameplay original et « caméléon ».
  • Design 3 — Brouillard : à réserver pour plus tard. En voie A c'est jouable, mais la version intéressante (voie B) demande de construire le tour par tour — utile seulement si on veut aussi Botnet & Don't Panic ensuite.
