SEC-1 CRITIQUE Secrets management Secrets exposés : fichiers .env trackés dans Git

Fichiers concernés

backend/.env backend/.env.dev messagerie/.env frontend/.env.local

Description

Les fichiers .env contiennent des secrets en clair et sont commit dans Git. Tout l'historique git du projet contient maintenant ces secrets — y compris d'éventuels forks, miroirs et caches GitLab.
  • APP_SECRET (Symfony, signe les CSRF/sessions)
  • JWT_PASSPHRASE pour les clés privées JWT
  • MAILER_DSN avec app password Gmail réel (ayrwjiknectnokcf)
  • STRIPE_SECRET_KEY (test mais à rotate par principe)
  • ADMIN_PASSWORD = Woc@Admin2026!$
  • MinIO creds admin / admin1234
Fix : (1) git rm --cached backend/.env backend/.env.dev messagerie/.env frontend/.env.local, (2) ajouter chaque .env* au .gitignore racine, (3) ROTATE TOUS LES SECRETS (changer APP_SECRET, JWT_PASSPHRASE, app password Gmail, mot de passe admin, MinIO), (4) créer .env.example sans valeurs réelles, (5) considérer git filter-repo pour purger l'historique si le repo va devenir public.
SEC-2 CRITIQUE ✅ FIXÉ Broken Access Control /api/upload accessible sans authentification

Fichier

backend/config/packages/security.yaml:28

Description

La règle { path: ^/api/upload, roles: PUBLIC_ACCESS } permet à n'importe qui d'uploader des fichiers (images ou ZIP) sans aucune authentification. Vecteurs : spam d'images (coût stockage MinIO illimité), hébergement de contenu illégal sur l'infra, upload de malware via ZIP (admis dans UploadConfig). Le frontend envoie déjà le JWT, donc rendre l'endpoint authentifié ne casse rien côté UX.
✅ Fix appliqué (commit feature-security) : ligne 28 de security.yaml changée en { path: ^/api/upload, roles: IS_AUTHENTICATED_FULLY }. Le frontend envoyait déjà le JWT (via uploadService.ts), aucune adaptation côté UI nécessaire.
SEC-3 CRITIQUE ✅ FIXÉ Privilege Escalation Premier inscrit devient ADMIN automatiquement

Fichier

backend/src/Controller/AuthenticationController.php:116-118

Description

if (count($userRepository->findAll()) === 0) { $user->setRole(UserRole::ROLE_ADMIN); }. Au premier déploiement en prod, le premier qui s'inscrit (via /api/register public) devient automatiquement administrateur. Combiné avec une absence de rate limit (SEC-5), un attaquant qui scanne le domaine peut s'auto-élever en admin avant même que tu te connectes.
✅ Fix appliqué (commit feature-security) : (a) bloc if (count(findAll()) === 0) { setRole(ADMIN); } retiré de AuthenticationController::register, (b) gestion des admins recentralisée : seed initial via les fixtures (AppFixtures.php crée déjà des comptes ROLE_ADMIN) et modification de rôle via le backoffice (interface admin existante), (c) test testRegisterGrantsAdminRoleToFirstUser renommé et asserte maintenant ROLE_USER même avec une DB vide.
SEC-4 CRITIQUE ✅ MITIGÉ Misconfiguration MinIO bucket en lecture publique anonyme

Fichier

docker-compose.yaml:155

Description

mc anonymous set download local/uploads rend le bucket "uploads" accessible publiquement. Combiné avec SEC-2, n'importe qui peut uploader n'importe quoi et tout le monde peut le télécharger. Le port 9000 MinIO est exposé sur l'host ("9000:9000") donc directement joignable depuis Internet si le serveur est ouvert.
✅ Fix appliqué (mitigation) (commit feature-security) : les clés S3 sont passées de <timestamp>-<filename> (énumérable) à <timestamp>-<32 hex chars>.<ext> avec bin2hex(random_bytes(16)) dans UploadController (128 bits d'entropie). Le bucket reste en download anonymous (autorise GET sur clé connue, pas LIST) — ce qui est acceptable maintenant que les clés sont imprévisibles. Test mis à jour pour valider le format.

⚠️ Note : ce fix ferme le vecteur d'attaque par devinette (qui est le risque réel), mais ne rend pas les uploads strictement privés. Pour une privacy totale (ex: posts privés à l'avenir), il faudra un proxy authentifié /api/uploads/{key} — chantier dépendant de SEC-7 (cookie httpOnly nécessaire pour que <img src> reste compatible).
SEC-11 CRITIQUE Misconfiguration STRIPE_WEBHOOK_SECRET non configuré (placeholder)

Fichier

backend/.env:49,55

Description

STRIPE_WEBHOOK_SECRET=whsec_REPLACE_ME. La vérification de signature du webhook utilisera ce placeholder. En prod, un attaquant peut envoyer un webhook fabriqué qui marque un Payment comme SUCCEEDED → le mentor reçoit l'argent crédité dans la DB sans aucun paiement réel.

SEC-13 CRITIQUE ✅ FIXÉ Broken Access Control Messagerie : userId envoyé par le client (usurpation d'identité)

Fichier

messagerie/src/index.js:91

Description

socket.data.userId = socket.handshake.auth?.userId;. Le JWT est validé correctement (ligne 88), mais le serveur écrase ensuite l'identité avec une valeur fournie par le client. Un user authentifié peut s'attribuer le userId d'un autre :
  • Recevoir les notifications privées de cible (rejoint la room user:<target>)
  • Apparaître online à la place de la cible
  • Envoyer des messages au nom de la cible dans les conversations dont elle est membre (le check participant en ligne 59-68 utilise senderId = userId)
✅ Fix appliqué (commit feature-security) : (a) côté backend, création de backend/src/EventListener/JWTCreatedListener.php enregistré dans services.yaml sur l'event lexik_jwt_authentication.on_jwt_created pour injecter userId dans le payload JWT au moment de la création, (b) côté messagerie (messagerie/src/index.js), remplacement de socket.data.userId = socket.handshake.auth?.userId par socket.data.userId = decoded.userId + check que le champ existe sinon rejet de la connexion. Le userId n'est désormais plus jamais contrôlé par le client.
SEC-14 CRITIQUE Broken Access Control Messagerie /api/notify sans authentification

Fichier

messagerie/src/index.js:19-52

Description

L'endpoint HTTP POST /api/notify n'a aucune vérification (pas de header, pas de secret, pas de JWT). Le backend Symfony l'appelle pour pusher des notifications, mais comme le port 8081 est exposé sur l'host ("8081:8081"), n'importe qui sur Internet peut envoyer des notifications fake à n'importe quel userId — vecteur de phishing puissant (faux message d'admin, fausse alerte 2FA, etc.).
Fix : ajouter un shared secret entre backend et messagerie, vérifié en début d'endpoint : if (req.headers['x-internal-secret'] !== process.env.INTERNAL_SECRET) return res.writeHead(401);. Et ne pas binder le port 8081 publiquement en prod (réseau Docker interne seulement, ou bind sur 127.0.0.1).

⏸️ Reporté : ce fix nécessite une nouvelle variable d'env partagée (modifications backend/.env, messagerie/.env, docker-compose.yaml). À traiter en même temps que SEC-1 (rotation globale des secrets) et SEC-11 (Stripe webhook secret) lors du sprint "secrets prod".

SEC-5 HAUTE ✅ FIXÉ Rate Limiting Pas de rate limiting sur /api/register

Fichier

backend/src/Controller/AuthenticationController.php:72-123

Description

Contrairement à /api/authenticate, register ne consomme aucun rate limiter. Permet : spam massif de comptes (DoS DB, saturation Gmail SMTP via 2FA), énumération d'emails (réponse 409 si existe vs 201 sinon), bypass d'éventuelles règles de modération en créant des dizaines de comptes.
✅ Fix appliqué (commit feature-security) : limiteur register_attempts ajouté dans config/packages/rate_limiter.yaml (sliding_window, 3 requêtes / heure par IP), injecté dans register() et consommé en tout début de méthode (clé = IP cliente) → renvoie 429 au-delà du quota. Couvert par le test testRegisterFailsWhenRateLimitIsExceeded.
SEC-6 HAUTE Secrets management Credentials MySQL/MinIO triviaux en dur dans docker-compose

Fichier

docker-compose.yaml:115-143

Description

MYSQL_ROOT_PASSWORD=root, MYSQL_PASSWORD=password, MINIO_ROOT_PASSWORD=admin1234. Le fichier docker-compose.yaml est commit. Le port MySQL 3306 est exposé sur 0.0.0.0:3306 du host par défaut. En prod tel quel = compromission totale (admin MySQL en root/root).
Fix : (1) docker-compose.prod.yaml séparé non-tracké pour les valeurs prod, (2) utiliser des Docker secrets ou variables d'env d'un .env.prod non commit, (3) ne pas exposer le port 3306 en prod (retirer la ligne ports: du service db), (4) mots de passe générés via openssl rand -base64 32.
SEC-7 HAUTE Session Management JWT stocké dans cookie non-httpOnly (vulnérable XSS exfiltration)

Fichier

frontend/src/contexts/AuthContext.tsx:73

Description

setCookie('token', token, { path: '/', maxAge: 14400 }) — aucune option httpOnly, secure, sameSite. Le JWT est lisible depuis document.cookie. Si une XSS est exploitée (même un bug obscur dans une dépendance, un message non sanitizé, une iframe inject), le token est exfiltré en 1 ligne JS.
Fix : faire poser le cookie côté backend dans la réponse /api/authenticate et /api/2fa/verify via Symfony\Component\HttpFoundation\Cookie avec ->withHttpOnly(true)->withSecure(true)->withSameSite('lax'). Le frontend ne lit plus le token directement : il appelle /api/me qui utilise le cookie. Le pattern actuel de stockage sessionStorage du tempToken 2FA souffre du même problème — à migrer aussi.
SEC-9 HAUTE ✅ FIXÉ Authentication Token de reset password sans expiration

Fichier

backend/src/Entity/User.php backend/src/Service/PasswordResetService.php

Description

Le champ resetToken n'a pas de champ resetTokenExpiresAt. Un UUID v4 est généré et reste valable indéfiniment tant qu'il n'est pas consommé. Si l'email est intercepté (boîte mail compromise un mois plus tard, leak, etc.), le token marche encore.
✅ Fix appliqué (commit feature-security) : champ resetTokenExpiresAt ajouté à User (+ migration Version20260615120000), mis à now()+1h dans requestReset(), et vérifié dans resetPassword() : un token expiré est refusé et purgé (token + expiration remis à null), sans changer le mot de passe. Couvert par les tests testResetPasswordWithExpiredTokenReturnsFalseAndClearsToken et la mise à jour du test de succès (810 tests au vert).
SEC-12 HAUTE Container Security Conteneurs Docker tournent en root

Fichiers

backend/Dockerfile backend/Dockerfile.prod frontend/Dockerfile messagerie/Dockerfile

Description

Aucun USER non-root configuré dans les Dockerfile. Tous les conteneurs tournent en UID 0. En cas d'exploit RCE (Symfony CVE, Node CVE, mediasoup, faille npm), l'attaquant a root dans le container → tentatives d'évasion plus faciles.
Fix : à la fin de chaque Dockerfile, créer et utiliser un user non-root. Exemple backend : USER www-data (déjà créé pour les permissions var/cache). Exemple Node : RUN useradd -m -u 1001 appuser && chown -R appuser /app && USER appuser.
SEC-15 HAUTE ✅ FIXÉ Misconfiguration Messagerie : CORS wildcard par défaut

Description

CORS_ORIGIN est déjà fourni dans messagerie/.env, .env.exemple et docker-compose.yaml, donc aucun impact dev/CI/docker.

SEC-8 MOYENNE ✅ FIXÉ Session Management JWT TTL trop long (4h) sans révocation possible

Fichier

backend/config/packages/lexik_jwt_authentication.yaml:5

Description

token_ttl: 14400 (4h). En cas de vol du JWT, l'attaquant a 4h sans aucun moyen de révoquer. L'industrie recommande 15-30 min avec refresh token. Le frontend rafraîchit déjà 30 min avant expiry.
✅ Fix appliqué (commit feature-security) : token_ttl: 900 (15 min) dans lexik_jwt_authentication.yaml — conforme OWASP (access token 5-15 min) et NIST SP 800-63B (AAL3 : inactivité ≤ 15 min). Côté frontend, la marge de refresh (AuthContext.tsx) qui était à « 30 min avant expiry » bloquait tout renouvellement pour un token de 15 min → remplacée par « 2 min avant expiry, ou à mi-vie » ; le maxAge du cookie aligné sur 900s dans AuthContext.tsx et authService.ts. Tests frontend verts (32) dont un test pré-cassé réparé. Optionnel non fait : blacklist Redis via claim jti pour un logout server-side.

SEC-19 MOYENNE ✅ FIXÉ Security Headers Aucun security header configuré

Description

Pas de Content-Security-Policy (XSS), Strict-Transport-Security (HTTPS forcé), X-Frame-Options (clickjacking), X-Content-Type-Options nosniff (MIME confusion), Referrer-Policy.
✅ Fix appliqué (commit feature-security) :
  • Frontend + backoffice (next.config.ts → headers()) : Strict-Transport-Security, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy et Permissions-Policy (caméra/micro autorisés pour soi côté frontend pour les appels vidéo, tout désactivé côté backoffice). Origines CSP dérivées des variables d'env.
  • Backend : SecurityHeadersSubscriber sur kernel.response (nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy, HSTS en HTTPS, CSP frame-ancestors 'none' — pas de default-src pour ne pas casser /doc). Couvert par SecurityHeadersSubscriberTest (3 tests).
À finaliser : le CSP frontend/backoffice est posé en Content-Security-Policy-Report-Only (déploiement OWASP-safe : observe les violations sans bloquer). À promouvoir en en-tête bloquant Content-Security-Policy après vérification navigateur (DevTools → Console, aucun rapport de violation).

SEC-21 MOYENNE ✅ FIXÉ XSS Sanitization HTML uniquement côté frontend (pas de défense en profondeur)

Description

Les posts/commentaires sont stockés en DB tels quels (HTML brut envoyé via l'API). La sanitization DOMPurify est seulement au rendu. Un futur client mobile ou un export qui afficherait sans sanitiser => XSS stocké. La modération texte bloque les insultes mais pas les balises <script>.
✅ Fix appliqué (commit feature-security) : symfony/html-sanitizer (v7.4) ajouté via Composer. Sanitizer app.user_content défini dans config/packages/html_sanitizer.yaml : preset « éléments sûrs » W3C (allow_safe_elements + allow_static_elements) — conserve la mise en forme et les médias réellement utilisés (img, video, liens, listes, code…) mais retire script, iframe, object/embed, les handlers on* et les URLs javascript:. Liens limités à http/https/mailto, rel="noopener noreferrer" forcé. (Cohérent avec le DOMPurify du frontend — ne casse pas les posts image/vidéo.) Injecté dans PostController (create / update / share) et CommentController (create / update), appliqué avant persistance (et avant la modération texte). Couvert par 2 tests dédiés (testCreatePostSanitizesHtmlBeforePersist, testCreateCommentSanitizesHtmlBeforePersist). Suite backend complète au vert (809 tests).
