SEC-1 CRITIQUE Secrets management Secrets exposés : fichiers .env trackés dans Git

Fichiers concernés

backend/.env backend/.env.dev messagerie/.env frontend/.env.local

Description

Les fichiers .env contiennent des secrets en clair et sont commit dans Git. Tout l'historique git du projet contient maintenant ces secrets — y compris d'éventuels forks, miroirs et caches GitLab.
  • APP_SECRET (Symfony, signe les CSRF/sessions)
  • JWT_PASSPHRASE pour les clés privées JWT
  • MAILER_DSN avec app password Gmail réel (ayrwjiknectnokcf)
  • STRIPE_SECRET_KEY (test mais à rotate par principe)
  • ADMIN_PASSWORD = Woc@Admin2026!$
  • MinIO creds admin / admin1234

Précision prod (k8s)

En prod, Vault écrase une partie de ces valeurs (DATABASE_URL, MINIO_SECRET_KEY, ELASTICSEARCH_PASSWORD) → pour celles-ci le risque est surtout l'historique git. En revanche ne sont PAS dans Vault (donc utilisés en prod depuis le .env commité) : APP_SECRET, JWT_PASSPHRASE, MAILER_DSN (Gmail). Ceux-là sont à la fois leakés ET actifs en prod → rotation prioritaire + à basculer dans Vault.
Fix : (1) git rm --cached backend/.env backend/.env.dev messagerie/.env frontend/.env.local, (2) ajouter chaque .env* au .gitignore racine, (3) ROTATE TOUS LES SECRETS (changer APP_SECRET, JWT_PASSPHRASE, app password Gmail, mot de passe admin, MinIO), (4) créer .env.example sans valeurs réelles, (5) considérer git filter-repo pour purger l'historique si le repo va devenir public.

Description

La règle { path: ^/api/upload, roles: PUBLIC_ACCESS } permet à n'importe qui d'uploader des fichiers (images ou ZIP) sans aucune authentification. SEC-4 CRITIQUE ✅ MITIGÉ Misconfiguration MinIO bucket en lecture publique anonyme

Fichier

docker-compose.yaml:155

Description

mc anonymous set download local/uploads rend le bucket "uploads" accessible publiquement. Combiné avec SEC-2, n'importe qui peut uploader n'importe quoi et tout le monde peut le télécharger. SEC-14 CRITIQUE ✅ FIXÉ (code) Broken Access Control Messagerie /api/notify sans authentification

Fichier

messagerie/src/index.js:19-52

Description

L'endpoint HTTP POST /api/notify n'a aucune vérification (pas de header, pas de secret, pas de JWT). Le backend Symfony l'appelle pour pusher des notifications, mais comme le port 8081 est exposé sur l'host ("8081:8081"), n'importe qui sur Internet peut envoyer des notifications fake à n'importe quel userId — vecteur de phishing puissant (faux message d'admin, fausse alerte 2FA, etc.).
✅ Fix appliqué (code) (commit feature-security) : secret partagé INTERNAL_SECRET entre backend et messagerie.
  • Messagerie (messagerie/src/index.js) : crash au boot si INTERNAL_SECRET absent ; /api/notify renvoie 401 si le header X-Internal-Secret ne correspond pas (comparaison à temps constant via crypto.timingSafeEqual).
  • Backend (NotificationService + services.yaml) : envoie le header X-Internal-Secret avec %env(INTERNAL_SECRET)%.
  • Dev : valeur dev-internal-secret-woc posée dans docker-compose.yaml (backend + messagerie), backend/.env, messagerie/.env(.exemple). Tests backend au vert (868).
⚠️ ACTION INFRA REQUISE — bloquant pour le déploiement prod
Les deux services crashent au boot si INTERNAL_SECRET n'est pas défini. Il faut donc, AVANT (ou pendant) le déploiement des nouvelles images :
  1. Générer un secret : openssl rand -hex 32 (une seule valeur, partagée).
  2. Vault — backend : ajouter la clé INTERNAL_SECRET dans secret/data/production/backend.
  3. Vault — messagerie : ajouter la même valeur sous INTERNAL_SECRET dans secret/data/production/messagerie.
  4. Helm — backend (cluster/backend/templates/deployment.yaml, annotation agent-inject-template-config) : ajouter une ligne export INTERNAL_SECRET="{{ .Data.data.INTERNAL_SECRET }}" (le fichier est déjà sourcé via . /vault/secrets/config).
  5. Helm — messagerie (cluster/messagerie/templates/deployment.yaml, même annotation, à côté de export DB_PASS=…) : ajouter export INTERNAL_SECRET="{{ .Data.data.INTERNAL_SECRET }}".
  6. Dev cluster : refaire les points 2→5 pour secret/data/… de l'environnement dev.
Vérif post-déploiement : kubectl -n production exec deploy/messagerie -- printenv INTERNAL_SECRET doit renvoyer la valeur, et les pods ne doivent pas être en CrashLoopBackOff.

Recommandé en plus : ne pas exposer le port 8081 publiquement en prod (réseau interne du cluster uniquement) — défense en profondeur au cas où le secret fuite.

SEC-7 HAUTE Session Management JWT stocké dans cookie non-httpOnly (vulnérable XSS exfiltration)

Fichier

frontend/src/contexts/AuthContext.tsx:73

Description

setCookie('token', token, { path: '/', maxAge: 14400 }) — aucune option httpOnly, secure, sameSite. Le JWT est lisible depuis document.cookie. Si une XSS est exploitée (même un bug obscur dans une dépendance, un message non sanitizé, une iframe inject), le token est exfiltré en 1 ligne JS.

SEC-12 HAUTE Container Security Pods k8s tournent en root (images sans USER, pas de securityContext)

Fichiers

backend/Dockerfile.prod frontend/Dockerfile.prod messagerie/Dockerfile.prod backoffice/Dockerfile.prod cluster/*/templates/deployment.yaml

Description

Concerne bien la prod (k8s), pas seulement le dev : les images Dockerfile.prod (utilisées par Kubernetes) n'ont aucun USER non-root, et les déploiements cluster/*/templates/deployment.yaml n'ont aucun securityContext (runAsNonRoot, runAsUser). Les pods applicatifs tournent donc en UID 0. En cas d'exploit RCE (CVE Symfony/Node, mediasoup, faille npm), l'attaquant a root dans le pod → évasion facilitée.
Fix : (1) ajouter un user non-root en fin de chaque Dockerfile.prod (USER www-data côté PHP, RUN useradd -m -u 1001 appuser && chown -R appuser /app && USER appuser côté Node) ; (2) ajouter un securityContext aux déploiements : runAsNonRoot: true, runAsUser: 1001, allowPrivilegeEscalation: false. (Action infra/Helm.)

État réel (k8s)

La prod fixe APP_ENV: "prod" (cluster/backend/values-prod.yaml:32) → le profiler et le firewall dev ne sont pas actifs en prod. Le risque résiduel se limite à : (a) une exploitation de CVE-2026-46626 (bascule APP_DEBUG via requête web) — patchée par SEC-18, et (b) le fait que symfony/web-profiler-bundle est embarqué dans l'image si elle inclut les require-dev.
Reste à faire (défense en profondeur) : (1) build prod sans les require-dev (composer install --no-dev dans Dockerfile.prod) pour exclure le web-profiler-bundle, (2) appliquer SEC-18 (patch CVE-2026-46626). Le point principal (APP_ENV) est déjà couvert par la conf k8s.
